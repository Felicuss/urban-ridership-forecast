# Задание: ИИ-прогноз загрузки трамвайных маршрутов

Трек хакатона Московского транспорта 2026 (МТТЕХ). Заказчик - Единый диспетчерский центр ГУП «Московский метрополитен». Оригиналы: [task_statement.pdf](source/task_statement.pdf) и текст со страницы платформы [platform_description.txt](source/platform_description.txt).

## Что прогнозируем

Число посадок на трамвайных маршрутах по часам. Посадка - одна успешная валидация (`validation_result == 1`), маршрут берётся из поля `ngpt_route`.

```
boardings(route, date, hour) = число успешных валидаций на маршруте route
                               за календарный час hour даты date
```

История есть за январь-октябрь 2025 (`train.csv` - январь-август, `test.csv` - сентябрь-октябрь). Прогнозируем 2025-11-01 … 2025-12-31, данных за этот период нет и не будет: эталон организаторы держат у себя. По сути это прогноз временного ряда на 61 день вперёд с часовым шагом.

Маршруты: `1, 5, 7, 11, 12, 17, 25, 26, 28, 50`. Маршрут 5 в данных встречается редко. Подробности о полях и файлах - в [dataset/README.md](../dataset/README.md).

## Формат сабмита

`submission.csv`, разделитель `;`, UTF-8, заголовок `route;date;hour;prediction`. Полная сетка ключей: 10 маршрутов × 61 день × 24 часа = 14 640 строк. `prediction` - число ≥ 0, при проверке округляется до целого. Шаблон - `dataset/test_submission.csv`.

Метрика:

```
WAPE       = Σ|y − ŷ| / Σy
WAPE-score = max(0, 1 − WAPE)
```

Шаблонный baseline из `test_submission.csv` даёт около 0.48. Как метрика переводится в баллы, описано в [evaluation.md](evaluation.md).

## Продуктовая часть

Кроме CSV нужен веб-сервис для диспетчеров. Его цель - распределять подвижной состав, снижать переполнение салонов и экономить на эксплуатации.

Горизонты прогноза: день с разбивкой по часам (обязательно), месяц, год (опционально, достаточно качественного прогноза).

Функциональные требования:

- агрегация прогноза по маршруту, остановке или участку и интервалу времени;
- интерактивный дашборд с картой Москвы: динамика пассажиропотока по времени в точках маршрута;
- выгрузка прогноза в CSV и/или XLSX;
- учёт времени суток, дня недели, сезонности и погоды, если есть данные;
- пайплайн приёма, нормализации и геопривязки исторических валидаций.

Нефункциональные требования. Сервис должен укладываться в один контейнер на 2-4 vCPU и 2-4 ГБ RAM и держать сотни RPS при p95 < 200-300 мс, CPU 60-80 % с запасом, без swap. Замеры производительности обязательно указать в README. Ещё нужны горизонтальное масштабирование, понятные ошибки API и возможность подключать внешние данные: погоду, трафик, стройки, новые маршруты.

Рекомендованный стек (не обязательный):

| Слой | Технологии |
|---|---|
| Backend | Java 21 LTS, Spring Boot 4.1.x, Spring WebFlux / Netty |
| Frontend | React 19+, TypeScript 5.x+ |
| ML | Python: scikit-learn, LightGBM, PyTorch; инференс в JVM через ONNX Runtime или DJL |
| Хранилище | PostgreSQL, ClickHouse или колоночные файлы |
| Карты | MapLibre, Leaflet или Yandex Maps API |
| Инфраструктура | Docker, Docker Compose |

## Геопривязка

Справочники в `dataset/spravochniki/` содержат GTFS-подобные таблицы (маршруты, остановки с координатами, порядок остановок, наряды, расписание) для маршрутов `1, 2, 3, 4, 5, 6, 7, 10, 11, 12`. С данными валидаций они пересекаются только по `1, 5, 7, 11, 12`. Поле `place_id` в валидациях - площадка или депо, а не остановка. Поэтому детализация до остановки - бонус для веб-сервиса, метрика считается на уровне маршрут × час.
