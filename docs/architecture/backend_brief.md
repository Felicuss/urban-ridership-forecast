## Стек

Рекомендация заказчика: Java 17+ (рекомендуется 21 LTS), Spring Boot 4.0+ (рекомендуется 4.1.x), Netty и WebFlux. Правило команды - последние версии библиотек, каждую сверяем через Context7 перед подключением. На машине стоит JDK 21.0.12, Maven и Gradle не установлены (будет wrapper), Docker Desktop с GPU есть, образов JDK нет.

Вопросы, которые решаем в начале работы по фактам: версия Java (21 из рекомендации или последняя LTS, если Spring Boot её поддерживает), Maven или Gradle, библиотека для XLSX (Apache POI SXSSF или FastExcel).

## Данные для сервиса

Модель остаётся на Python и работает офлайн. Сервис только читает готовые артефакты, модели в запросе не запускаются.

Что уже есть в репо:
- сабмиты в `forecasts/`: лучший на лидерборде `submission_ex_ante_route5.csv` (0.89950, скрипт `analysis/s32_ex_ante_route5.py` поверх `s30`), его сервис и отдаёт по умолчанию. Он собирается без foundation-моделей, поэтому экспорт артефактов не требует кэша FM и GPU;
- коэффициенты вариантов в `forecasts/coefficients_*.json`;
- геометрия в `external/osm_tram_routes.geojson`, остановки маршрутов 1, 5, 7, 11, 12 со справочником в `dataset/spravochniki/`.

Чего не хватает, первым шагом делаем на Python: экспорт каталога `artifacts/` по контракту из ревью (п. 7.1).
- `manifest.json`: версия модели, коммит, forecast_origin, sha256 и число строк файлов;
- `forecast_components.csv`: route, date, hour, base, множители факторов и override. Одного JSON коэффициентов мало, потому что правила s10 заменяют значения целиком (выходные 7 и 50, маршрут 5, 31.12);
- `coefficients.json` со схемой ползунков: значение по умолчанию, диапазон, источник;
- остановки и доли для раскладки, `network.geojson`, помесячный прогноз на год.

Формула пересчёта (ревью, п. 7.1): pred = base_variant × Π m_i^{x_i} × (1 - x_free) + route5_on × route5_workday × u5 × m_event.

## Архитектура

- Слои: domain (чистые расчёты без Spring), application (сценарии: прогноз, агрегация, сценарный пересчёт, выгрузка), infrastructure (загрузка и проверка артефактов), api (WebFlux, DTO, ошибки RFC 9457). Границы слоёв закрепляет тест архитектуры.
- Данные загружаются один раз при старте, проверяются по manifest и хранятся как неизменяемые примитивные массивы с индексом маршрут × дата × час. Срез интервала - это арифметика индексов без поиска.
- Пересчёт сценария идёт векторно по массивам. Одинаковые наборы коэффициентов кэшируются по хэшу.
- Всё, что может блокировать (выгрузка XLSX, большие CSV), выполняется на отдельном пуле, ответы отдаются потоком.
- Сервис без состояния, OpenAPI генерируется из кода, чтобы фронт мог сразу по нему работать.

## Какие тесты нужны

Проверяем то, что может сломаться незаметно и стоить баллов. Тесты ради покрытия не пишем.

1. Эталонный тест: при коэффициентах по умолчанию пересчёт совпадает с выбранным сабмитом во всех 14 640 ячейках.
2. Согласованность агрегации: часы складываются в сутки и месяц без потерь, сумма по остановкам равна прогнозу маршрута.
3. Правила: 31.12 после 20:00 ноль у всех маршрутов, маршрут 5 до 16.12 18:00 ноль, выходные 7 и 50 до и после 15.11.
4. Контракт API через WebTestClient: параметры, коды ответов, ошибки в формате RFC 9457 на неверный маршрут, дату, горизонт или коэффициент вне диапазона.
5. Выгрузка: число строк, BOM и разделитель CSV, XLSX открывается и содержит те же суммы, кириллица в имени файла по RFC 6266.
6. Проверка артефактов при старте: неверный sha256 или число строк останавливает запуск с понятной ошибкой.
7. Тест архитектуры: domain не зависит от Spring и инфраструктуры.

Нагрузка проверяется отдельно сценарием k6, результат идёт в README.
