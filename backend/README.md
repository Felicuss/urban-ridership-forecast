# Час пик: сервис прогноза загрузки трамваев

REST API для диспетчера. Сервис отдаёт почасовой прогноз посадок на ноябрь-декабрь 2025 по маршруту, остановке, участку или всей сети, агрегирует его по суткам и месяцам и даёт годовой прогноз. Прогноз пересчитывается по ползункам и событиям, для тепловой карты есть кадры по часам. Выгрузка идёт в CSV и XLSX. Открыть можно любую дату с 1 января 2025 по 31 октября 2026: январь-октябрь 2025 - факт из данных организаторов, ноябрь-декабрь 2025 - прогноз модели, январь-октябрь 2026 - оценка по сезонности городского трамвая с коридором ±12 %. По умолчанию сервис отдаёт лучший конкурсный прогноз v6 `forecasts/submission_shape_facts_v6.csv` (WAPE-score 0.90553) без единого расхождения: формула профиля в каждой ячейке домножается на поправку до v6, и ползунки сдвигают v6 так же, как сдвигали бы формулу.

Стек: Java 25, Spring Boot 4.1.1, WebFlux на Netty, Jackson 3, springdoc-openapi 3.1.1, Caffeine 3.3.0, FastExcel 0.20.2, Gradle 9.7.1. Модель остаётся на Python и работает офлайн, сервис читает только готовые артефакты из [`../artifacts`](../artifacts/README.md).

## Запуск

Из корня репозитория:

```
docker compose up -d --build              # http://localhost:8080: интерфейс и api за nginx
docker compose up -d --scale api=3        # три реплики за тем же адресом
docker compose down
```

Порт меняется переменной `API_PORT`, адрес фронта для CORS - `CORS_ORIGINS`. Контейнер api ограничен 2 vCPU и 2 ГБ без swap, как в ТЗ.

Без Docker нужен JDK 21 или новее для самого Gradle, JDK 25 для сборки он скачает сам:

```
cd backend
./gradlew bootRun      # http://localhost:8080, артефакты из ../artifacts
./gradlew test
```

Документация API: `/swagger-ui.html`, схема OpenAPI: `/api/v1/openapi`. По ней фронт может сгенерировать клиента.

## API

Время везде местное, Europe/Moscow. Посадки - успешные валидации, как в метрике. Каждая точка ряда идёт с медианой, коридором p10-p90 и источником `source`: `fact` (коридора нет, p10 = p90), `forecast` или `outlook`. Сценарий меняет только `forecast`.

| Метод и путь | Что делает |
|---|---|
| `GET /api/v1/forecast` | Ряд прогноза. `level=route\|stop\|segment\|network`, `id`, `from`, `to`, `granularity=hour\|day\|month`, `hours=7-9`, `horizon=day\|month\|year`. Для участка ещё `direction`, `fromStop`, `toStop` |
| `POST /api/v1/forecast/scenario` | Пересчёт по ползункам и событиям: ряд сценария, базовый ряд и разница по каждой точке |
| `GET /api/v1/coefficients` | Ползунки: значение по умолчанию, диапазон, шаг, источник |
| `GET /api/v1/network` | Трассы по направлениям и остановки в GeoJSON, с ETag |
| `GET /api/v1/network/load?date=&hours=` | Кадры тепловой карты: посадки каждого маршрута и остановки по часам даты. `POST` - то же по сценарию |
| `GET /api/v1/export?format=csv\|xlsx` | Выгрузка маршрутов, остановок, участка или сети за интервал. Для участка один маршрут в `ids`, `direction`, `fromStop`, `toStop`. `POST` - то же по сценарию |
| `GET /api/v1/meta` | Версия модели, дата прогноза, скор на лидерборде, качество на бэктесте, область применимости, границы шкалы времени `timelineFrom` и `timelineTo` |
| `GET /api/v1/calendar` | Каждый день шкалы: тип дня, выходной, праздник, источник данных |
| `GET /api/v1/factors` | Внешние данные для панели факторов: погода, календарь, пробки, поездки на трамвае по месяцам, расписание, события. С ETag |
| `GET /api/v1/routes`, `/api/v1/routes/{route}/stops`, `/api/v1/stops` | Маршруты, их остановки с долями посадок, все остановки |
| `GET /actuator/health` | Проверка живости и готовности для балансировщика |

Горизонты из задания:

```
GET /api/v1/forecast?level=route&id=17&horizon=day&from=2025-11-03        # сутки по часам
GET /api/v1/forecast?level=stop&id=g6153&horizon=month&from=2025-12-01    # месяц по дням
GET /api/v1/forecast?level=network&horizon=year                           # ноябрь 2025 - октябрь 2026 по месяцам
GET /api/v1/forecast?level=route&id=17&from=2025-11-01&to=2025-11-30&granularity=day&hours=7-9   # утренний пик за ноябрь
```

Сценарий: декабрь на 5 % выше и перекрытие маршрута 17 в субботу днём.

```json
POST /api/v1/forecast/scenario
{
  "query": {"level": "route", "id": "17", "horizon": "month", "from": "2025-12-01"},
  "coefficients": {"level_dec": 1.085},
  "events": [{"route": 17, "from": "2025-12-06", "to": "2025-12-06", "hours": "10-18", "multiplier": 0, "label": "перекрытие"}]
}
```

Ответ несёт итоговые значения всех ползунков: фронт сверяет по ним своё состояние. Одинаковые сценарии берутся из кэша. Если сценарий новый, вся сетка из 14 640 ячеек пересчитывается за доли миллисекунды, так что ползунки можно отправлять с debounce 150-200 мс.

Ошибки идут в формате Problem Details (RFC 9457), все нарушения сразу:

```json
{
  "type": "urn:tramload:problem:validation",
  "title": "Запрос вне области определения модели",
  "status": 400,
  "detail": "id: маршрута 99 нет в прогнозе, доступны [1, 5, 7, 11, 12, 17, 25, 26, 28, 50]; from: дата 2026-01-05 вне горизонта прогноза 2025-11-01 - 2025-12-31",
  "instance": "/api/v1/forecast",
  "errors": [
    {"field": "id", "message": "маршрута 99 нет в прогнозе, доступны [1, 5, 7, 11, 12, 17, 25, 26, 28, 50]"},
    {"field": "from", "message": "дата 2026-01-05 вне горизонта прогноза 2025-11-01 - 2025-12-31"}
  ]
}
```

Выгрузка CSV идёт в UTF-8 с BOM, разделитель «;», поэтому Excel открывает её сразу. Имя файла кириллицей передаётся через `filename*` по RFC 6266. Выгрузка всех маршрутов по часам за горизонт совпадает с сабмитом построчно. Полная сетка «остановка × час» занимает около 660 тыс. строк и помещается на один лист XLSX.

## Как устроен

```
analysis/s40_export_artifacts.py  ->  artifacts/ (manifest.json с sha256)
                                          |
infrastructure   ArtifactLoader: проверка sha256 и числа строк, разбор, самопроверка формулы
                                          |
domain           ForecastModel (неизменяемые массивы маршрут × дата × час), ForecastEngine,
                 Aggregator, StopNetwork, CoefficientCatalog - чистая Java без Spring
                                          |
application      QueryResolver, ForecastService, ScenarioService (кэш Caffeine),
                 NetworkLoadService, ExportService
                                          |
api              WebFlux-контроллеры, DTO, Problem Details, потоковая выгрузка
```

- Данные читаются один раз при старте, около 220 мс. Каждый файл сверяется с `manifest.json` по sha256 и числу строк. Потом формула со значениями по умолчанию сверяется с прогнозом, который посчитал экспорт на Python. Если код и артефакты разошлись, сервис не запускается и называет файл и причину.
- Прогноз хранится в плоских массивах `double[]`. Ячейка = (маршрут × 61 + день) × 24 + час, поэтому срез интервала - это арифметика индексов без поиска.
- `ForecastEngine` повторяет правила `analysis/s10_forecast.py` в том же порядке операций. Формула описана в [`artifacts/README.md`](../artifacts/README.md).
- Остановки и участки - оценка. Прогноз маршрута раскладывается по долям остановок, сумма по остановкам равна маршруту. Остановки посадки в валидациях нет, так что измерить её нельзя.
- Сервис не хранит состояния, поэтому масштабируется репликами. nginx раз в 10 секунд перерешивает имя `api` через DNS Docker и сам подхватывает `--scale api=N`. Сжимает ответы тоже nginx, так что процессор реплик уходит только на расчёт.
- Расчёты занимают микросекунды и идут прямо на потоках Netty. Выгрузка пишется в `OutputStream` на виртуальном потоке через `DataBufferUtils.outputStreamPublisher` и уходит частями по 64 КБ.

## Тесты

Тесты написаны на то, что может сломаться незаметно и стоить баллов, а не ради покрытия. `./gradlew test` прогоняет 46 тестов примерно за 10 секунд на настоящем каталоге `artifacts/`.

| Тест | Что защищает |
|---|---|
| `ForecastEngineGoldenTest` | Прогноз по умолчанию совпадает с лучшим сабмитом во всех 14 640 ячейках. На пяти наборах коэффициентов из `artifacts/golden/` формула совпадает с исходными правилами на Python с точностью 1e-9. Сломанное правило 31.12 роняет шесть тестов |
| `ForecastRulesTest` | Правила событий: 31.12 после 20:00 ноль на всех маршрутах, маршрут 5 возит пассажиров только с 16.12 18:00, выходные 7 и 50 возвращаются 15.11, ползунок даты возврата сдвигает скачок |
| `AggregationConsistencyTest` | Часы складываются в сутки и месяцы, остановки - в сеть, участок из всех остановок направления равен половине маршрута |
| `ApiContractTest` | Контракт для фронта: форма ряда, ячейка против сабмита, годовой горизонт, Problem Details на неверный маршрут, дату, месяц, горизонт, шаг, окно часов и ползунок, сбор всех ошибок сразу, разница сценария, перекрытие, ETag, 404 |
| `ExportTest` | CSV всех маршрутов по часам равен сабмиту, BOM и «;», в XLSX те же суммы, кавычки в названиях остановок, кириллическое имя файла |
| `ArtifactLoaderTest` | Изменённый файл, неверное число строк, пропавший файл и расхождение формулы с экспортом останавливают запуск с понятной ошибкой |
| `ArchitectureTest` | Доменный слой не зависит от Spring, Jackson и других слоёв, вызовы идут только сверху вниз |

## Производительность

Замер k6 2.3.0 в открытой модели нагрузки (`constant-arrival-rate`). Запросы приходят с заданной частотой, как бы медленно ни отвечал сервис, поэтому хвосты задержек не занижаются. Прогон: разогрев 30 с, дальше по 60 с на каждой частоте. Смесь запросов как у диспетчера:

- 60 % - маршрут на сутки;
- 25 % - остановка на сутки;
- 10 % - сценарий с новым значением ползунка почти в каждом запросе, то есть пересчёт всей сетки;
- 5 % - выгрузка CSV маршрута за месяц.

Путь запроса: k6 в своём контейнере (2 vCPU) -> nginx -> api (`cpus: 2`, `mem_limit: 2g`, без swap). Машина: Ryzen 5 5600X, 32 ГБ, Windows 11, Docker Desktop 29.5.3 на WSL2. Повторить замер: `docker compose up -d`, затем `RATES=100,300,500 ./deploy/k6/run-load.sh`. Сырые результаты лежат в [`deploy/k6/results/`](../deploy/k6/results).

| Частота, запросов/с | Реплик | p50, мс | p95, мс | p99, мс | Ошибок | CPU api, % от 2 vCPU | Память api |
|---|---|---|---|---|---|---|---|
| 100 | 1 | 0.51 | 0.75 | 0.92 | 0 | 1.5 | 393 МБ |
| 300 | 1 | 0.48 | 0.66 | 0.90 | 0 | 3.7 | 393 МБ |
| 500 | 1 | 0.46 | 0.62 | 0.85 | 0 | 5.6 | 393 МБ |
| 1000 | 1 | 0.46 | 0.68 | 1.67 | 0 | 18.5 | 343 МБ |
| 2000 | 1 | 0.44 | 0.65 | 2.74 | 0 | 25.8 | 342 МБ |
| 3000 | 1 | 0.48 | 0.76 | 3.32 | 0 | 37.4 | 343 МБ |
| 4000 | 1 | 0.48 | 0.93 | 7.06 | 0 | 43.1 | 366 МБ |
| 2000 | 3 | 0.48 | 1.01 | 2.37 | 0 | 8-16 на реплику | - |

Все частоты выдержаны без пропущенных итераций. Самый тяжёлый запрос, сценарий с пересчётом всей сетки, на 4000 запросов/с даёт p95 1.1 мс и p99 7.6 мс. ТЗ требует сотни запросов в секунду при p95 < 200-300 мс и загрузке CPU 60-80 %. На 500 запросах/с одна реплика тратит 6 % своих 2 vCPU и отвечает с p95 0.6 мс. На 4000 запросах/с она занята на 43 %, а p95 всё ещё меньше 1 мс, так что запас по частоте не меньше чем в 8 раз. Выше 4000 запросов/с не проверяли: k6 и nginx работают на той же машине, что и сервис. На трёх репликах nginx распределил 2000 запросов/с между всеми тремя.

## Ограничения

- Почасовой прогноз есть только на 2025-11-01 - 2025-12-31. Январь-октябрь 2026 - качественный помесячный прогноз с коридором ±12 %, сценарий на него не влияет.
- Остановки и участки - раскладка маршрута по долям. Доли оценены по порядку остановок, фактическую остановку посадки из валидаций не восстановить.
- Порядок остановок маршрутов 17, 25, 26, 28 и 50 взят из OpenStreetMap: в справочнике организаторов этих маршрутов нет.
- Коридор p10-p90 построен по ошибкам бэктеста для маршрута. У суммы ряда коридор - сумма коридоров точек, он шире реального.
- Новый маршрут или изменение трассы задаются событием с множителем. Чтобы добавить маршрут с собственной формой суток, нужно пересобрать артефакты на Python.
